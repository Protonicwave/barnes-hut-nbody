What the tree buys, and what it costs

Two questions decide whether the tree is worth using. How much faster is it than summing every pair, and how much accuracy does it give up? Each figure answers one, with direct summation as the reference.

Accuracy

The tree changes the answer in two separable ways: it approximates each force, and that error feeds into the integration. The first figure isolates the force. The second runs the same orbit with direct summation at the same timestep and softening, so any gap above it belongs to the tree.

How it works

Four choices set the behaviour of the code. Each one is tested, and each states what it gives up.

The opening test

A cell stands in for its particles only when it is far enough away. The distance d from the particle to the cell's centre of mass must exceed s/θ + δ, where s is the cell's side and δ is how far its centre of mass sits from its geometric centre. The plain test s/d < θ fails for particles near the edge of a large cell (Salmon and Warren 1994), which the offset term fixes (Barnes 1994). The default is θ = 0.5, and values above about 0.7 are not recommended (Dehnen 2002).

d > sθ + δOpen the cell unless this holds

The integrator

Kick-drift-kick leapfrog with one fixed timestep for every particle. It is symplectic, so with a fixed step the energy error stays bounded instead of growing steadily. Variable steps would break that guarantee, so they are left out.

v ← v + ½Δt a
x ← x + Δt v
a ← a(x)
v ← v + ½Δt a

Softening

Plummer softening adds ε2 to the squared distance, so a close pair cannot produce an unbounded acceleration. The softening length is a physical choice, so the code has no default for it. This page starts at 4/√N and lets you try 1/√N and 2/√N.

ai = Σj≠i mj (xj − xi)(|xj − xi|2 + ε2)3/2G = 1

The three setups

A Plummer sphere in virial units is the equilibrium case. A cold collapse starts a uniform sphere at rest and is the stress case, where energy error is hard to judge. A two-body Kepler orbit has an exact answer, so it checks the integrator on its own, with no tree involved.

Use it

The same core builds as a C++ library, installs as a Python module and runs here in the browser.

From Python

The module returns NumPy arrays. Positions are a read-only view onto the simulation's memory, so reading them does not copy.

# from a clone of the repository: pip install .
import numpy as np
import barnes_hut as bh

positions, velocities, masses = bh.plummer_sphere(4096, seed=1)
simulation = bh.Simulation(
    positions, velocities, masses,
    dt=1 / 128, softening=4 / np.sqrt(4096),
    method="tree", theta=0.5, threads=8,
)
simulation.step(256)

From C++

CMake 3.25 or later. The workflow presets configure, build and run the tests in one command. bench/check_budgets.py checks the budgets in the table above against a benchmark run, and the README gives the commands.

git clone https://github.com/Protonicwave/barnes-hut-nbody
cd barnes-hut-nbody
cmake --workflow --preset dev
cmake --workflow --preset release

In the browser

The threaded build needs two response headers on every file the page loads. Without them the browser withholds shared memory, and the page falls back to the single-threaded build. The simulation looks the same either way and runs more slowly on one thread. GitHub Pages cannot set these headers. web/_headers sets them on Cloudflare Pages, and python web/serve.py serves the directory locally with them.

  • Cross-Origin-Opener-Policy: same-origin
  • Cross-Origin-Embedder-Policy: require-corp

Where this sits

REBOUND, FDPS and GADGET-4 are the established codes in this area, and Bonsai is a GPU tree code. The closest browser project is nbody-simulator-webgl, which builds CPU, GPU and Barnes-Hut simulations from C++ to WebAssembly. This project adds threaded WebAssembly with a published scaling plot, a Python module you can install with pip, and an energy analysis checked against direct summation.
